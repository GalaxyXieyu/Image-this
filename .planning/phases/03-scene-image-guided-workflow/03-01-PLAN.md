# Phase 3 Plan: Scene Image Guided Workflow

## Goal

把 `/workspace/scene` 从三步 UI 原型推进为可执行的场景图生成闭环：模板预设进入 draft，用户补充商品信息和参考素材，提交真实任务，轻量轮询状态，展示候选结果，并把结果保存到结果管理。

## Scope

- `/workspace/scene` 场景图三步流程
- scene preset 到 draft 初始化
- 商品信息、平台、场景、卖点、风格、参考素材的数据结构
- input asset 引用链路
- scene generation 任务创建 adapter
- `/api/tasks/status` 轻量轮询
- 模型列表获取和 provider 调用相关的 `main` 分支调整需要选择性合入当前分支
- 最小 build 和 smoke 验证

## Out of Scope

- 不做完整 `/api/workflow/*` endpoint 系列。
- 不重构整个 `src/app/api/tasks/worker/route.ts`。
- 不删除旧 workspace。
- 不迁移 preset 到 DB。
- 不实现完整智能工具箱。
- 不新增 AI provider。

## Execution Waves

### Checkpoint 0: Sync main model-call and model-list changes

目标：把 `main` 分支中和模型调用、模型列表获取、provider 配置兼容性相关的调整选择性合入当前工作台分支，避免 Phase 3 的 scene/task adapter 建在过期模型能力上。

Tasks:

1. Compare `main` against current branch for these areas:
   - `src/app/api/models/route.ts`
   - `src/lib/image-processor/**`
   - `src/app/api/settings/route.ts`
   - `src/app/api/tasks/**`
   - `src/app/api/images-process/**`
   - provider-specific API routes: `qwen`, `jimeng`, `volcengine`
   - user/provider config helpers
2. Identify only model-call/model-list related changes; avoid unrelated UI, docs, packaging, or route cleanup.
3. Merge relevant changes selectively, preserving current Phase 3 planning and `/workspace/scene` edits.
4. If task type/model mapping changed on `main`, update scene task adapter plan before Wave 2 implementation.
5. Verify `/api/models` and model-dependent task creation still behave with current provider settings.

Deliverables:

- A short list of main-side model changes selected for this branch.
  - `/api/models` uses `main` behavior for OpenAI-compatible model discovery, including `toapis.com` compatibility.
  - Gemini model discovery merges remote model IDs with the `main` fallback image/model ID list.
  - Worker result records use asset `clientUrl` or persisted URLs for original/reference/logo fields instead of storing large data URLs in result metadata.
  - Provider implementation files under `src/lib/image-processor/**` had no selected diff in this checkpoint.
- Relevant code changes merged without broad branch merge.
- Phase 3 Wave 2 adapter uses the up-to-date model/provider contract.

Acceptance:

- `/api/models` uses the same model discovery behavior as the selected `main` updates.
- Scene workflow default `aiModel` values remain compatible with available model IDs.
- No current Phase 3 planning files or scene draft edits are overwritten.

### Wave 1: Scene draft and preset initialization

目标：让模板库进入场景工作流时，页面拥有稳定的初始 draft，而不是只携带 URL 参数。

Tasks:

1. Map `TemplatePreset.params` into a scene draft shape.
2. Update `/workspace/scene` to read `?preset=` and initialize scene draft.
3. Replace page-local `WorkflowData` with a shape aligned to `SceneWorkflowDraft` where practical.
4. Preserve user edits after preset initialization.
5. Show active preset/style in the scene workflow UI.
6. Keep `/templates → /workspace/scene?preset={id}` navigation stable.

Deliverables:

- Scene preset initializes product/style/default generation fields.
- Scene page can explain which preset is active.
- No behavior change to non-preset direct entry.

Acceptance:

- Opening `/workspace/scene?preset={scenePresetId}` initializes visible draft values.
- Opening `/workspace/scene` without preset still starts from empty/default draft.

### Wave 2: Input assets and task submission adapter

目标：把“参考图 + 商品信息 + 风格选择”变成可提交的真实任务输入，同时避免回退到 base64 和页面内任意 JSON 拼装。

Tasks:

1. Wire reference upload area to existing input asset upload/register flow.
2. Store reference images as asset references or client URLs, not base64 blobs.
3. Add a centralized scene task input builder or reuse `adaptToLegacyTaskRequest` if compatible.
4. Ensure scene generation task type maps consistently to current worker expectations.
5. Create task(s) through existing `/api/tasks` compatibility path.
6. Trigger worker path only if existing task flow requires it and current behavior supports it.

Deliverables:

- Reference asset list in scene draft.
- Centralized scene task input mapping.
- Real task creation on generate.
- Implemented in Wave 2:
  - `src/lib/workbench/scene-task-adapter.ts` converts scene draft + product asset + reference asset into `/api/tasks` legacy-compatible requests.
  - Scene generation is temporarily mapped through the current `BACKGROUND_REMOVAL` worker branch with compact `inputAsset` / `referenceAsset` references and `customPrompt` scene guidance.
  - `/workspace/scene` uploads product and reference images through `/api/input-assets`, creates one task per candidate, and exposes created task IDs in the candidate cards.
  - No `SCENE_GENERATION` task type is submitted to the existing worker in this wave.

Acceptance:

- Clicking generate creates at least one real `TaskQueue` task.
- Created task payload contains compact references and scene metadata, not uploaded base64.
- Task center can see the created task.

### Wave 3: Lightweight polling and candidate result state

目标：用轻量状态接口驱动候选结果，不再用 mock result cards 表示任务完成。

Tasks:

1. Replace local `setInterval(fetch /api/tasks/:id)` with `useWorkflowTaskPolling` or equivalent `/api/tasks/status` polling.
2. Map task statuses into candidate card states.
3. Display progress, completed, failed, and cancelled states clearly.
4. Show provider/worker error messages through existing error mapping where available.
5. Connect completed task result data to candidate cards if result payload provides URLs/assets.
6. Keep polling bounded and avoid duplicate completion handling.

Deliverables:

- Candidate result state is derived from task status.
- Failure states are visible and understandable.
- Polling uses lightweight status path.
- Implemented in Wave 3:
  - `/workspace/scene` stores created task IDs per candidate and starts `useWorkflowTaskPolling` after successful `/api/tasks` creation.
  - Candidate cards now render real `pending` / `processing` / `completed` / `failed` / `cancelled` state, progress, current step, task ID, error message, and result image URL when provided by `/api/tasks/status`.
  - `/api/tasks/status` returns compact summaries with normalized lowercase status, `legacyStatus`, `workflowType`, progress, current step, error message, and parsed result URL without returning large `inputData` / `outputData` blobs.
  - Task center, recent task surface, floating task button, and workbench adapters share task compatibility naming through `src/lib/workbench/task-compat.ts`.
  - Scene generation remains a legacy-compatible `BACKGROUND_REMOVAL` task at worker ingress, while UI/status surfaces preserve `scene_generation` business semantics through `inputData.workflowType`.

Acceptance:

- Generate flow visibly progresses from pending/processing to completed/failed.
- No large payload is fetched in the status loop.

### Wave 4: Result save, integration checks, and phase closeout

目标：让用户能从候选图进入结果管理，并形成可验证的 Phase 3 完成证据。

Tasks:

1. Add save/select behavior for completed candidate results.
2. Connect saved result to existing `/results` surface or existing image record API.
3. Keep task center visibility intact.
4. Run `npm run build`.
5. Perform smoke checks for `/templates`, `/workspace/scene`, `/tasks`, `/results`, `/settings`.
6. Create `03-01-SUMMARY.md` and `03-VERIFICATION.md` after implementation.
7. Update `.planning/ROADMAP.md` and `.planning/STATE.md` when Phase 3 is complete.

Deliverables:

- Save/selection behavior for generated scene candidates.
- Build verification evidence.
- Phase summary and verification report.

Acceptance:

- A user can complete the minimal chain: template → scene draft → generate task → see status/result → save or inspect result.
- `npm run build` passes.

## Implementation Guardrails

- Do not touch unrelated dirty changes.
- Do not remove old workspace yet.
- Do not place large image data in task status or polling payloads.
- Keep worker edits narrow; Phase 5 handles broad worker contract refactor.
- Prefer feature-level helpers over adding more state into one page component.
- Keep task type mapping centralized enough to avoid drift between UI, worker, task center, and result rendering.

## Risks

- Existing worker may not fully support `SCENE_GENERATION` result payloads; if so, Phase 3 should add the smallest compatibility layer and record remaining worker refactor for Phase 5.
- Scene result persistence may currently be tool-oriented; save behavior may need adapter mapping.
- Browser-visible UI can be ahead of backend capability; avoid marking Phase 3 complete until a real task/result chain is verified.

## Success Criteria

1. `/workspace/scene` can read scene presets and initialize draft state.
2. Scene draft includes product info, platform, scene, selling points, style, generation count, and input asset references.
3. Generate creates real task(s) with compact input references.
4. Polling uses lightweight task status endpoint.
5. Candidate cards reflect real task statuses and result data where available.
6. User can save/select completed results into the existing result management path.
7. Existing settings, tasks, results, auth/provider config, and Electron baseline remain reachable.
8. Build passes.

Current status after Wave 3:

- Criteria 1–5 are implemented at contract/code level.
- Criteria 6–8 remain Wave 4 / closeout work.
- Real provider completion, worker trigger behavior, storage URL accessibility, and browser smoke path still need manual verification before business验收。

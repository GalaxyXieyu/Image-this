# Phase 4 Plan: Unified Smart Toolbox

## Goal

把 `/tools` 从同步处理型工具页改造成统一智能工具箱：共享上传、参数、画布、结果、任务状态和结果管理链路，至少覆盖 AI 换背景、加水印、高清化和扩图。

## Scope

- `/tools` 统一三栏工作台
- 工具选择和参数草稿
- 工具 preset 初始化
- input asset 引用上传
- 工具任务创建 adapter
- `/api/tasks/status` 轻量轮询
- 结果预览和结果管理入口
- 最小 build 和 lint 验证

## Out of Scope

- 不实现完整 `/api/workflow/tool` endpoint。
- 不重构整个 `src/app/api/tasks/worker/route.ts`。
- 不删除旧处理接口。
- 不做高级 canvas 编辑器。
- 不做真实 batch group 持久化。
- 不做 Electron/Windows 完整回归。

## Execution Waves

### Wave 1: Toolbox workbench shell and task-based execution

目标：用统一工具箱数据模型替换 `/tools` 的同步处理心智，让单图工具可以创建真实任务、轮询状态、展示结果。

Tasks:

1. Define a small tool draft shape inside `/tools` or helper module.
2. Map supported tools to typed workflow types and default parameters.
3. Upload input image through `/api/input-assets` and keep `InputAssetRef` in draft.
4. Build legacy-compatible task request through existing `adaptToLegacyTaskRequest`.
5. Submit tool run to `/api/tasks`.
6. Poll status via `useWorkflowTaskPolling` and `/api/tasks/status`.
7. Show current task status, progress, result image, failure state, task link, and result link.
8. Preserve `/tools` route and current navigation.

Deliverables:

- `/tools` still renders as a unified workbench.
- At least background replace, watermark, upscale, and outpaint can submit real tasks.
- Tool result state is task-driven, not direct synchronous endpoint-driven.

Acceptance:

- Upload image → choose tool → apply effect creates a real task.
- `/tasks` can see the created task.
- Candidate/result panel updates through lightweight status polling.
- No large payload is fetched in the status loop.

### Wave 2: Tool preset initialization and parameter coverage

目标：让模板库工具 preset 真正初始化 `/tools` 的选中工具和参数，减少模板入口和工具箱之间的断层。

Tasks:

1. Read `?preset=` on `/tools`.
2. Load preset from `src/lib/workbench/presets.ts`.
3. If preset is a tool preset, initialize selected tool, parameter defaults, and batch mode.
4. Show active preset name/description in the toolbox.
5. Keep direct `/tools` entry stable.
6. Add watermark text/logo defaults, upscale factor, outpaint scale, background prompt controls.

Deliverables:

- `/templates → /tools?preset={id}` or equivalent can initialize the tool draft.
- Parameter controls are visible and editable for supported tools.

Acceptance:

- Tool preset navigation changes visible tool state.
- User edits override preset defaults without being reset unexpectedly.

### Wave 3: Result save semantics and phase closeout

目标：把工具结果管理行为和 Phase 3 场景结果保持一致，形成可验证的 Phase 4 完成证据。

Tasks:

1. Ensure completed tool tasks can be inspected from `/tools`.
2. Confirm worker-created or saved results appear in `/results` with correct category mapping.
3. Add any missing result save fallback only if worker output does not create `ProcessedImage` consistently.
4. Run focused lint and `npm run build`.
5. Perform smoke checks for `/tools`, `/tasks`, `/results`, `/templates`, `/settings`.
6. Create `04-01-SUMMARY.md` and `04-VERIFICATION.md`.
7. Update `.planning/ROADMAP.md` and `.planning/STATE.md` when Phase 4 is complete.

Deliverables:

- Result inspection and result management path for supported tools.
- Verification evidence.
- Phase summary and verification report.

Acceptance:

- A user can complete the minimal chain: tool preset or direct tools → upload → submit task → see task status/result → inspect result in `/results`.
- `npm run build` passes.

## Implementation Guardrails

- Do not touch unrelated dirty changes.
- Do not remove old processing APIs.
- Do not place large image data in task status or polling payloads.
- Keep worker edits narrow; Phase 5 handles broad worker contract refactor.
- Keep tool type mapping centralized enough to avoid drift between UI, API, worker, task center, and result rendering.
- Prefer adapter/helpers over adding more ad-hoc JSON assembly in the page.

## Verification Plan

### Automated

1. Focused ESLint for edited files.
2. `npm run build` before closeout.
3. Type/lint diagnostics for edited files where available.

### Manual Smoke

1. Open `/tools`.
2. Upload one image.
3. Select background replace and create a task.
4. Confirm task appears in `/tasks`.
5. Confirm status updates in `/tools`.
6. Repeat quick submit checks for watermark, upscale, and outpaint where provider/config allows.
7. Confirm completed result can be inspected from `/results`.
8. Confirm `/settings` remains reachable.

## Risks

- Existing worker may not create result payloads consistently across all tools.
- Some providers may require user credentials or image hosting configuration.
- Watermark logo and advanced canvas editing are larger than first-wave scope; text watermark is the safe baseline.
- Broad worker/API contract cleanup is intentionally deferred to Phase 5.

## Success Criteria

1. `/tools` uses one unified workbench structure.
2. Tool draft includes selected tool, input asset, parameters, batch mode, task state, and result summary.
3. At least background replace, watermark, upscale, and outpaint can create real tasks.
4. Tool task status is driven through `/api/tasks/status`.
5. Result preview and `/results` path are visible.
6. Existing task center, settings, results, provider config, and direct processing APIs remain reachable.
7. Build passes before phase closeout.

# Phase 1 Plan: Product Visual Workbench Foundation

## Goal

Create the foundation for rebuilding Imagine This into the new AI product visual workbench without carrying forward the old monolithic workspace UI.

## Scope

This phase changes structure and foundation, not every final screen. It should make later implementation faster by defining routes, layout primitives, state contracts, and typed API boundaries.

## Tasks

1. Inventory reusable versus disposable frontend code.
   - Mark `src/app/workspace/page.tsx` as replace-target.
   - Identify shared components that can survive: upload area, image preview, watermark editor internals, result modal logic, task progress display.
   - Identify old tab/sidebar orchestration as deletion candidates.

2. Define the new route map.
   - Decide final URLs for homepage, template library, scene workflow, and toolbox pages.
   - Add route-level placeholders that use the new shell.
   - Keep old `/workspace` behavior behind a temporary route or redirect only if needed during migration.

3. Create workbench layout primitives.
   - `WorkbenchShell`
   - `WorkbenchTopNav`
   - `WorkbenchSidebar`
   - `WorkbenchCanvas`
   - `WorkbenchDetailPanel`
   - `WorkbenchActionBar`
   - `StepBar`

4. Establish design tokens and visual rules.
   - Match the Pencil design's neutral palette, borders, panel widths, typography scale, and compact controls.
   - Avoid nested card-heavy layouts.
   - Add CSS variables or Tailwind utility conventions in the existing styling system.

5. Define workflow domain types.
   - Create typed entities for `SceneWorkflow`, `ToolRun`, `TemplatePreset`, `BatchGroup`, `WorkflowTask`, and `GeneratedAsset`.
   - Separate client draft state from persisted task/result state.

6. Create typed API contract layer.
   - Define request/response schemas for new workflow task submission.
   - Map new workflow types to current `TaskQueue.type` values through a compatibility adapter.
   - Keep existing `/api/tasks` functioning during this phase.

7. Centralize task polling model.
   - Replace page-local polling assumptions with a reusable hook/service that can support batch groups and individual items.
   - Preserve current task list API until the new response contract is implemented.

8. Add foundation verification.
   - Typecheck/build the new route/component skeleton.
   - Add basic smoke coverage or a manual checklist for the route shell.
   - Confirm no provider behavior changed.

## Deliverables

- New feature folders for the workbench foundation.
- New typed workflow/API contract files.
- Route skeletons for the new IA.
- Migration notes documenting old UI deletion candidates.
- Build passes with old provider/task behavior preserved.

## Risks

- The old workspace page has a large amount of behavior mixed into one component; deleting it too early could lose edge-case logic.
- Current `TaskQueue.inputData` stores arbitrary JSON strings, so typed contracts need adapters before database changes.
- Electron packaging may depend on route assumptions and should be checked before removing old entry points.

## Verification

- Run `npm run build`.
- Run targeted lint/type checks if available.
- Manually open core routes in dev server:
  - `/`
  - `/templates`
  - `/workspace/scene`
  - `/tools/background`
  - `/tools/watermark`
- Confirm settings/auth pages remain reachable.
